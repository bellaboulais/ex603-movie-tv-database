## Modelling Justification
In the Users relation, I created a User_Id, because a user’s email, although unique, can change and we want that primary key to be stable. For Movies, I used the Movie_Id as the primary key, because there may be multiple movies with the same title. I created a composite primary key for ratings, because I wanted to enforce that a single user can rate a movie once, so having (User_Id, Movie_Id) uniquely identifies their rating for that movie. I used Genre_Id for consistency, even though I also enforce the Genre string to be unique and non null. Lastly, for Movie_Genres, I chose to make another composite primary key, because it has a one-to-many relationship with both movies and genres, so a movie can have multiple genres and vice versa.

I chose to make all my foreign keys CASCADE ON DELETE. In the ratings table, if a user is deleted, their ratings should also be deleted, and if a movie deletes, its ratings should be removed from the table. I considered letting the ratings stay if a user gets deleted and set the User_Id to null, but I’d have to have a Ratings_Id for the primary key, and in the future, if the user re-joins and rates the movie again, it would conflate the rating score to have their rating twice. I also assume, if the user deletes their account instead of just not using the platform, they want their data deleted from the platform. In the Move_Genres table, if a movie or genre is deleted this row should also be deleted as the relationship no longer exists. 

The rules I enforced in the schema help maintain data integrity whether or not they are explicitly handled by the application. The primary keys ensure that each user, movie, and genre has a unique identifier, while the composite primary key on Ratings prevents a user from rating the same movie more than once. If a user wants to update their rating, that is up to the application, but if they were allowed to make multiple ratings it could conflate the average score that the other users will see and make judgements on. The foreign key constraints ensure that ratings and movie-genre relationships can only reference existing records. For example, if a genre is deleted, a user could try to search it if they saw it still attached to a movie by the Movie_Genres entity. I enforced unique genre names for searching capabilities and unique email addresses for security purposes in case verification is later needed for a User_Id. I also made a rule for ratings to fall within a valid numeric range so the average score is not affected by incorrect data.


## Reflection
One decision I made is to use a composite key for ratings (User_Id, Movie_Id), which enforces the rule that a user can only rate a movie once. I then made the foreign keys "ON DELETE CASCADE", which removes ratings if the associated user account or movie is deleted. A different designer could argue that the table should have a separate Rating_Id, allowing multiple ratings for the same user and preserving ratings after a user deletes their account. This could be beneficial if a user watches the same movie again and wants to include their new rating to reflect their current opinion. However, this introduces risk if a user inputs multiple high (or low) ratings that conflate the average score. I think the composite key simplifies reads and writes, because queries do not need to distinguish between multiple ratings from the same user, and the database automatically rejects a duplicate rating rather than requiring the application to check for one first.
